# 桌面小组件设计（2026-10-08）

> 目标平台按 **Android** 设计（本项目出 APK 验证）。iOS 差异见第八节。

## 一、先看限制 —— 限制决定了设计长什么样

小组件不是"App 的一小块界面"。它跑在**别人的进程**里，这是所有约束的根源。

**1. 小组件的画面由桌面（launcher）绘制，不是我们的 App。**

Android 桌面小组件用 `RemoteViews` 渲染 —— 一份可序列化、能跨进程传递的 View 描述，
launcher 拿到它自己画出来。由此推出三条：

- **能画的东西极其有限**。RemoteViews 支持的 View 是固定的一小撮：
  没有动画、没有滚动、没有手势。`react-native-android-widget` 让你用 JSX 写布局，
  但组件会被**映射成 RemoteViews**，所以只能用它提供的那几个
  （`FlexWidget` / `TextWidget` / `ImageWidget` / `ButtonWidget` 等），
  不是任意 RN 组件，样式也受限（无复杂渐变、无阴影）。
- **数据必须在"交给 launcher 之前"准备好**。生成那份描述的时刻，是系统唤起的一次
  "没有界面的 App 进程"（库注册的 Task Handler）—— JS 确实能跑，
  但它**有时间预算**，而且**不保证我们自己的数据库已经初始化完毕**，
  不能指望在那里现读 `expo-sqlite`。
- **launcher 永远拿不到"活"的数据**，只有一份拍好的快照。

**2. 什么时候刷新由系统说了算。**

- `updatePeriodMillis` **最小 30 分钟**，且 Doze 模式下不可靠（实测常被推迟到几小时）。
- 想更频繁只能上 `WorkManager`，它的周期下限是 **15 分钟**——但那是给"必须自己拉数据"的场景准备的。
- 我们这种 App **基本不需要**（理由见第三节）。

**3. 必须 development build。** 任何 widget 库都含原生代码，Expo Go 里跑不了。

**4. ⚠️ 官方 `expo-widgets` 目前是 iOS-only。** 它用 `@expo/ui` 声明式写布局、
在独立 JS 运行时里算出布局树、再由原生侧用 SwiftUI 重建 —— 整套是 iOS 的。
多个来源一致确认（社区包里明确写着 "expo-widgets is currently iOS-only"）。
**所以 Android 只能走 `react-native-android-widget`（第三方，Android-only，MIT）。**
它的配套是 Expo config plugin + `app.plugin.ts`，集成方式跟我们已经写过的悬浮球模块同源。

> ⚠️ 名字陷阱：`react-native-android-widget` 与 `react-native-android-widgets`（多个 s）
> 是**两个不同的包**，后者是第三方作者的跨平台方案（用截图 `WidgetCanvas` 把 RN 视图
> 拍成图传给小组件，画质与动态性都更差）。装错一个字母就是另一条技术路线。

**5. 一个附带结论：小组件的设计自由度远低于 App 内界面。**
所以设计顺序应该是 —— 先问"这一格里最小必要的信息是什么"，而不是"App 里那张卡怎么塞进去"。

## 二、数据从哪来 —— 唯一需要新建的基础设施

小组件读不到数据库，那就**由主进程把渲染需要的东西写成一份快照**，小组件只读快照。

```
App 主进程（有 sqlite）
   │  refresh() 之后，算一份"小组件要显示的东西"
   ▼
快照（JSON）
   │  写进一个"能被快速读到的轻量容器"
   ▼
渲染小组件的那一刻（可能是一个没有界面的 App 进程）
```

**这套东西我们已经写过一次了。** `modules/overlay/`（悬浮球）就是一个自写 Local Expo Module，
走的正是"原生侧持有状态、JS 侧给个门面"的路子。小组件的数据出口可以直接加在同一个模块里，
或按同样的形状新建一个 `modules/widget-bridge/`。

⚠️ **具体落在哪个容器，要实测后再定，不要先写死。** 两条路各有说法：

- **SharedPreferences（经自写原生模块）**：有一位同时维护 iOS/Android 小组件一年的开发者
  明确说"App 与小组件进程分离，**不能共享 AsyncStorage**"，他自己写了 `widget-storage` 模块
  来绑 SharedPreferences / App Group UserDefaults。
- **AsyncStorage（项目已有这个依赖）**：它在 App 进程内可用，而 Android 的小组件渲染
  （`react-native-android-widget` 的 Task Handler）是在**没有界面的 App 进程**里跑的，
  理论上读得到；但 headless 环境下的初始化和可靠性需要实机确认。

**阶段 1 的第一件事就是把这个测出来** —— 用一个临时页面/临时小组件读写一次，
几分钟就能见分晓。选错容器不会让设计推翻，只会让阶段 1 返工一次。

快照里放什么，是**设计决策**而不是实现细节 —— 它决定了小组件能显示什么。
原则：**只放渲染直接要用的东西，不搬整张表**。理由有二 ——
① 快照要序列化，搬全表是浪费；② 小组件不该有机会显示"数据库里有什么"，
只该显示"我们决定让它显示的东西"。

## 三、什么时候更新快照 —— 一个让复杂度大幅下降的判断

**日程类 App 的数据变化，几乎全部由用户在 App 内的操作触发。**

勾掉一件事、记一条新的、改了课表 —— 这些动作发生时，主进程**一定正在运行**，
顺手推一次快照就行，零延迟。真正需要系统帮忙的只有两件事：

1. **跨天**（午夜过后今天是新的一天，昨天的任务不该再挂着）；
2. **时间流逝**（"还有 20 分钟上课"变成"还有 5 分钟"）。

这两件事，**30 分钟的刷新粒度完全够用** —— 跨天最多差半小时，而"还有多久上课"
这种文案本来也不需要精确到分钟（写成"14:00 上课"比"还有 23 分钟"更耐用，
而且不依赖刷新频率）。

**所以：不用 WorkManager，不用后台轮询。** 主进程主动推 + 系统低频刷新兜底。

代价是"App 从没打开过时，小组件显示的是上次的快照"。对日程 App 这是可接受的 ——
用户没打开 App，说明他没在安排事情。

## 四、分类：做哪几个

小组件的格子是稀缺资源（桌面就那么几格，用户不会给你的 App 三格）。
**第一版只做两个**，各自回答一个好问题：

| 优先 | 小组件 | 回答的问题 | 建议尺寸 |
|---|---|---|---|
| ① | **今天** | 现在该做什么 | 中（4×2）起，可自适应到 2×2 |
| ② | **下一节课** | 接下来要去哪 | 小（2×2） |

其余是候选，不是第一版：

| 候选 | 判断 |
|---|---|
| 课程表（全天） | 信息量大，需要大尺寸（4×4）才成立；且"下一节课"已覆盖 80% 的即时需求 |
| 专注快启 | 只有动作没有信息 —— 用 Android 的 **app shortcut**（长按图标）更省格子 |
| 收集箱快记 | 同上，长按图标 → 「记一件事」即可 |
| 统计 / 热力图 | 桌面不是看统计的地方。要看的人会进 App |

## 五、两个小组件的设计

### ① 今天（4×2，可缩到 2×2）

**显示**：今天剩下的任务标题，按时间排，最多 3 行；一行前面一个状态点。

```
┌──────────────────────────────┐
│ 今天 · 还剩 3 件              │
│  ○ 交实验报告        14:00   │
│  ○ 数据结构作业      20:00   │
│  ○ 买电池            今天    │
└──────────────────────────────┘
```

**不做的事（都很诱人，都要拒绝）**：

- **不放进度环 / 完成率**。桌面不是仪表盘，而且"今天做了几件"是个会让人焦虑的数字。
- **不放"现在做哪件"的唯一答案**。首页的专注卡之所以能这么干，是因为它同时给出**理由**，
  在小格子里理由放不下，只剩一个不带解释的结论 —— 那跟替用户做决定没区别。
  这条要跟既有约定对齐：**一句话结论必须带得出理由，否则不上桌面**。
- **不放"添加"按钮**。widget 上加"＋"会让人以为必须在桌面加，
  真正的记录入口是长按图标（shortcut）和 App 里的浮动按钮。

**点击**：整块 → 打开 App（落在首页）。逐行点击（`ButtonWidget`）后做，第一版不做 ——
行高在 4×2 里只有 ~28px，太窄，点击容易误触。

**缩到 2×2 时**：只显示"还剩 3 件" + 第一件的标题。

**更新**：勾完一件立刻推；跨天由系统刷新兜底。

### ② 下一节课（2×2）

**显示**：

```
┌────────────────┐
│ 下一节          │
│ 数据结构        │
│ 14:00–15:40    │
│ 南海 A302       │
└────────────────┘
```

**没课时**显示"今天没课"（不要留空、不要显示"暂无数据"）。
**放假 / 学期外**显示"学期还没开始"或"学期结束了" —— 这跟首页 `NextCourseCard` 是同一份口径
（`domain/course.ts` 里已有现成的推算），不要在小组件里另写一套。

**为什么用绝对时刻而不是倒计时**：见第三节 —— 倒计时依赖刷新频率，
而绝对时刻任何时候看都是对的，还少一次刷新需求。

**更新**：课表变更时推；每节课结束后由系统刷新兜底换到下一节（30 分钟粒度足够，
因为相邻两节课之间至少隔一个课间）。

## 六、分阶段落地

**阶段 0（前置）**：打包链路打通 —— 小组件必须真机验证，而真机验证卡在出包上。

**阶段 1（数据出口）**：
新建 `modules/widget-bridge/`（或并入 `modules/overlay/`），提供一个
"把快照写进 SharedPreferences / 读出来"的门面；在 `app-store.refresh()` 之后调用。
**这一步可以在没有小组件的情况下先做完并验证**（用一个临时页面把快照打出来看），
不需要等打包 —— 是本机就能推进的部分。

**阶段 2（今天组件）**：接入 `react-native-android-widget`，写 Task Handler 读快照渲染。
这一步开始必须真机。

**阶段 3（下一节课组件）**：复用同一份快照（快照里一次写全两个组件要的数据）。

**阶段 4（自适应尺寸 + 打磨）**：处理 2×2 到 4×2 的布局切换、深色模式、预览图。

## 七、验收清单

- [ ] 小组件在 App 完全没运行过时**不空白**（显示快照或"还没安排"）
- [ ] 在 App 里勾掉一件事，桌面小组件**立刻**跟着变
- [ ] 跨天（改手机时间到明天）后小组件显示新的一天，且**不超过 30 分钟**延迟
- [ ] 深色模式下文字可读
- [ ] 2×2 与 4×2 两种尺寸都不出现文字截断/重叠
- [ ] 点击整块 → 正确落到 App 首页

## 八、iOS 差异（等有了 iPhone 真机再谈）

- iOS 用官方 `expo-widgets`（`@expo/ui` 写布局），数据出口是 **App Group UserDefaults**，
  与 Android 的 SharedPreferences 是同一个角色、不同的容器。
- iOS 的刷新由 **WidgetKit timeline** 管理 —— 是"提前排好一串未来的数据"，比 Android 更可控。
- 所以数据出口这一层要**按平台分叉**，但快照的内容（JSON 结构）两边可以共用。
